Early prototype · self-hosted · AGPL-3.0-or-later

A household display that runs in your house, not in someone else's.

Canvas drives a calm screen on a wall or a television from hardware you own. No account, no cloud tenancy, no third party in the data path. One command starts it, and it needs no configuration to do something useful.

It is an early prototype. One part of it — the ambient photo display — runs every day on a real household television. The rest is a tested model layer with no editor in front of it yet. This page distinguishes between the two rather than averaging them.

What Canvas is

A display server, a portable document format for screens, and one working screen built on top of them.

01

A screen, not a control panel

A household display is a shared surface. Everyone in the house sees it, and so does every visitor. Canvas is built to be read from across a room and ignored the rest of the time — not to be poked at.

The snapshot endpoint issues GETs and exposes no way to call a service. A compromised display cannot actuate anything in the house, because there is no code path that would let it.

02

Documents you can read

Screens are plain JSON — hand-editable, diffable, and version controllable. Unknown fields and unknown block types written by a newer build survive a load and save cycle by an older one, so a document shared between two households does not rot.

03

Who it is for

Someone who already runs a container or two at home, wants a wall display, and would rather not hand their household's photos, calendar and presence to a subscription. You need a machine, a screen, and a willingness to read a README.

If you want a finished product with an editor, Canvas is not that yet. Commercial dashboard products are.

Where the data actually goes

Canvas is self-hosted. It runs as a single container on hardware you own, keeps its state in a volume you control, and has no account with anyone. There is no telemetry and no analytics in the codebase.

Credentials never reach the browser. If you connect a home automation server or a photo provider, the server process holds those tokens, calls those APIs itself, and returns only the shaped fields the screen renders. The page never sees a token, an entity id, or a raw upstream payload.

That is a real boundary and it is worth stating its limits: if you configure an outside photo provider or weather source, Canvas makes outbound requests to it from your server. That is not local processing and this page will not describe it as such. Configure nothing and Canvas talks to nobody — it starts and runs that way by default.

The ambient display

The strongest thing Canvas does today, and the only part that has been running unattended in a real house.

A photo, a line, and the weather

Full-bleed photograph, a quote of the day with its attribution, and current conditions. That is the whole screen. It is designed to be glanced at, which means most of the design work went into what it refuses to put on the wall.

Each data source degrades independently. A missing photo key means no photo, not a blank screen; an unreachable automation server means no house state, not an error page. The display keeps working with whatever it still has.

445 quotes, attributed honestly

The library ships 445 entries with hedged attributions — where a line is widely misattributed, it says so rather than repeating the confident version. Attribution is treated as an obligation, not a caption.

Selection is author-spaced, so the same author never appears on two consecutive days. A naive shuffle produced adjacent repeats often enough to look broken, so ordering is computed rather than random.

docs/05 — ambient screen

The ambient screen is still a spike in the repository's own terms: it does not yet use the canonical document model described below. It works, and it is honest about being a prototype rather than the finished architecture.

Running it

Three ways, in the order we would recommend them. The container needs no configuration and no API keys to start; every integration is optional.

  1. Clone and compose

    The default, because it is the one where you can read everything before you run it. You get the source, the Dockerfile, and the compose file in front of you, and nothing executes until you decide. 

    $ git clone https://github.com/vhark/CommonHome-Canvas.git
$ cd canvas
$ docker compose up

    Then open http://localhost:4174/. No .env file is needed; the compose file treats one as optional on purpose, so a fresh clone starts rather than failing on a file full of blanks. Copy .env.example only if you want an integration.

  2. A single docker run

    One command, no clone, nothing written to your working directory except a named volume. Useful for trying it on a spare machine. 

    $ docker run --rm -p 4174:4174 ghcr.io/vhark/commonhome-canvas:latest

    Not published yet. There is no image on a public registry at the time of writing, so the command above will fail. Until one is pushed, the equivalent is a clone and a local build: 

    $ docker build -t commonhome-canvas .
$ docker run --rm -p 4174:4174 commonhome-canvas

  3. The convenience script

    There is an install script that does the above for you. The usual way to run it is to pipe it straight into a shell, and the usual way is worth thinking about for a moment first.

    Piping a script to a shell means trusting the source completely — the server that answers that URL, the TLS chain to it, and whoever can change what it returns. It is not worse than any other way of running someone else's code, but it is the only one where you never see the code.

    So download it, read it, then run it. It is short, and the point of publishing it is that you can check it. 

    $ curl -fsSL https://raw.githubusercontent.com/vhark/CommonHome-Canvas/main/scripts/install.sh -o install.sh
$ less install.sh
$ sh install.sh

    If you have read it once and want the one-liner afterwards, it is curl -fsSL https://raw.githubusercontent.com/vhark/CommonHome-Canvas/main/scripts/install.sh | sh. We are not going to pretend we do not know you will use it; we would rather the caveat was on the same page.

Canvas has zero runtime dependencies. The container ships the display and a standalone Node HTTP server and nothing else — no node_modules, no build toolchain, no package manager invoked at runtime. It runs read-only, as a non-root user, with no new privileges.

How it works, briefly

Two bodies of code that do not import each other, and one boundary between the household's credentials and the screen.

The canonical model

src/canvas/ holds the real core: the portable document schema, named density levels at 6, 12 and 24 columns, declared block footprints, and a pure deterministic reflow function. No I/O, no DOM, no clock, no randomness.

Covered by 50 passing tests including property tests for round-trip, idempotence, containment and preservation. It is a model layer: no UI, no editor, no persistence.

docs/04 — grid density

The server

A standalone Node HTTP server using only the standard library. It serves the built display, answers a health check that never depends on an integration being configured, and exposes one read-only snapshot endpoint.

Configuration is entirely environment-driven, with a host allowlist and no household value left in the source.

docs/01 — architecture

The spikes

spikes/ holds disposable experiments: a grid engine comparison harness and the ambient screen. The repository says so in the first line of the files themselves rather than in a footnote.

They are scheduled for removal once they have answered the questions they were written to answer. The ambient screen graduates when it is rebuilt on the canonical model.

Where this actually stands

Working means implemented in this repository and covered by tests you can run yourself. It does not mean production-ready. There is no editor, no database, no authentication, no publishing and no display pairing. Do not run this as a service you depend on.

The gap between the tested model layer and the working screen is the project's main structural risk — they are not yet the same system. That is tracked in the open rather than smoothed over.
